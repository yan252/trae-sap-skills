# CDS 开发对象命名规则

## 一般规则

开发对象的常规指导原则如下：`[/<namespace>/][<prefix>]_<object_name>_[<suffix>]`

### 使用命名空间
使用为组织保留的自有命名空间。

> **备注**：请注意，命名空间 `/DMO/` 保留用于演示目的。不要在生产开发中使用此命名空间。

### 使用前缀
当一个开发对象具有一般不同类型的情况下，使用前缀。此前缀表示无法通过对象类型传达的语义差异。

例如，服务绑定可以将用于 UI 的 OData 服务公开为 Web API。因此，对于服务绑定，我们引入了前缀 `UI_` 和 `API_` 以区分服务绑定的语义。

### 对象名称
`<object_name>` 指的是 IDE 中定义的资源库对象的名称。它可以是基于业务语义的语义名称，用于指示资源库对象的内容。

### 使用后缀
后缀用于额外区分不同类型的开发对象。它有助于识别开发对象中的更细微或次要差异。

例如，UI 服务可以绑定到 OData 协议 OData version 2 和 OData version 4。通过将名称后缀为 `_O2` 或 `_O4`，也可以体现出这种差异。

> **备注**：在 ABAP 航班参考场景中，我们使用其他后缀字符（`_R`、`_M`、`_D`、`_U`、`_C`）。该字符标识属于一个特定开发指南（只读、托管、草稿、非托管、服务使用）的开发对象。

## ABAP 字典对象

### 数据库表
在场景中使用数据库表的前缀，在这种情况下，相同语义数据的多个技术表示是必要的，例如在草稿场景中。

| 前缀 | 说明 |
|------|------|
| `A_` | 持久数据库表（即包含活动数据的表） |
| `D_` | 草稿数据库表 |

**示例**：`/DMO/A_TRAVEL_D`

---

## CDS 对象

### CDS 实体

| 前缀 | 说明 |
|------|------|
| `I_` | 接口视图 |
| `R_` | 基本 CDS 视图实体 |
| `C_` | 映射视图（字符 C 表示使用层） |
| `E_` | 扩展 include 视图 |

使用后缀 `TP` 指示 CDS 视图与事务处理相关。

**示例**：`/DMO/R_AGENCYTP`、`/DMO/C_Travel_Processor_M`

### 行为定义
行为定义始终与业务对象的根实体具有相同的名称。

**示例**：`/DMO/R_AGENCYTP`、`/DMO/C_Travel_M`

### 元数据扩展
元数据扩展与其相关的 CDS 实体具有相同的名称。如果为一个 CDS 实体使用多个元数据扩展，则可以添加编号的后缀。

**示例**：`/DMO/C_TRAVEL_U`、`/DMO/C_BOOKING_U_M2`

---

## 业务服务

### 服务定义
由于作为业务服务一部分的服务定义没有不同的类型或不同的规范，因此（通常）不需要前缀或后缀来区分含义。

**示例**：`/DMO/TRAVEL_U`

但是，在计划不为 UI 和 API 服务重用同一服务定义的用例中，前缀可以遵循服务绑定的规则。

**示例**：`/DMO/UI_TRAVEL_U`

### 服务绑定

| 前缀 | 说明 |
|------|------|
| `UI_` | 服务作为 UI 服务公开 |
| `API_` | 服务公开为 Web API |

| 后缀 | 说明 |
|------|------|
| `_O2` | 服务绑定到 OData 协议版本 2 |
| `_O4` | 服务绑定到 OData 协议版本 4 |

**示例**：`/DMO/UI_TRAVEL_U_O2`

---

## 源代码对象

### 行为池

| 前缀 | 说明 |
|------|------|
| `BP_` | 实施业务对象行为的 ABAP 类 |

**示例**：`/DMO/BP_TRAVEL_U`

### 处理器和保护程序类

| 前缀 | 说明 |
|------|------|
| `LHC_` | 本地处理器类 |
| `LSC_` | 本地保护程序类 |

根据行为实施的模块化，可以在类名称中提供编码的语义。

**示例**：`LHC_TRAVEL_CREATE`、`LHC_BOOKING_CUD`
